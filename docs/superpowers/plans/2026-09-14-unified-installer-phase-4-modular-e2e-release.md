# Unified Installer Phase 4 — Modular CLI and End-to-End Release Plan

> **Execution:** implement on the existing `docs/unified-installer-design` branch and PR #363. Do not open a second PR for this work. The PR is merged only after the staging release path exercises the exact installer, CLI, server archives, and Docker image together.
>
> **Required discipline:** TDD. Every new helper, generator, workflow contract, and staging harness starts with a failing test. Existing black-box installer tests remain the behavior oracle.

## Goal

Finish the unified installer end to end without expanding the current monolith:

1. Keep `scripts/zosma` as one dependency-free POSIX executable for raw-URL installation.
2. Move its maintainable source into ordered modules and generate the executable deterministically.
3. Complete the Phase 4 server-release workflow: four server archives, stamped CLI, checksums, manifest, image digest, attestations, exact-artifact smoke tests, release upload, and stable promotion.
4. Add a manual/staging path that publishes temporary prerelease artifacts and runs the real branch bootstrap before merge, without changing the stable channel or requiring production DNS.
5. Update public documentation only after the staging path passes.

## Current baseline and constraints

- `scripts/zosma` is approximately 2,631 lines and contains 119 functions. The largest units are configuration parsing, local installation, manifest parsing, and option parsing.
- The one-file **shipped artifact** is intentional. The one-file **source layout** is not required by the release contract and is the maintainability defect being corrected.
- `install.sh` already supports `ZOSMA_TESTING=1` plus `ZOSMA_TEST_MANIFEST_URL`; production resolution remains fixed to the stable URL or an exact GitHub release version.
- Existing installer tests use temporary roots, fake commands, and fixture manifests. They must continue to run unchanged against the generated `scripts/zosma` artifact.
- Existing `server-release.yml` is the Phase 2 image workflow. Phase 4 must extend it without weakening the desktop release workflow.
- No production stable pointer, DNS record, public release, or real credential is touched by PR/staging tests.
- Supported local targets remain `linux-x64`, `linux-arm64`, `darwin-x64`, and `darwin-arm64`. Windows, system-wide installs, Tailscale, Kubernetes, and public internet exposure remain out of scope.

## Architecture decisions

### A. Modular source, single generated executable

Create an ordered source tree:

```text
scripts/zosma-src/
  00-preamble.sh             # shebang, constants, set -eu
  10-output-validation.sh    # output, errors, pure validators
  20-paths-config.sh         # XDG roots and config/secrets parsing
  30-manifest.sh              # release manifest and checksum parsing
  40-files-generations.sh     # markers, links, generation helpers
  50-transactions.sh          # journal persistence and recovery
  60-platform-services.sh     # archive verification and service templates
  65-terminal-platform.sh      # terminal seam and platform probes
  70-install-local.sh         # install request parsing and local runtime activation
  75-install-docker.sh        # Docker install/update helpers
  80-lifecycle.sh             # serve/start/stop/restart/status/logs/open/doctor/access
  90-update-uninstall.sh      # update, reinstall, uninstall, purge
  99-main.sh                  # command dispatch and final main invocation
```

The initial extraction is mechanical: preserve function order, globals, comments, output, exit codes, and command invocation semantics. Do not “clean up” behavior while splitting. Cross-module dependencies are resolved by ordering, not by runtime `source` calls.

The release artifact remains `scripts/zosma`. It is generated by `scripts/build-zosma.mjs`, using Node built-ins only. The generator must:

- read the fixed ordered fragment list;
- reject missing, duplicate, or empty fragments;
- join fragments with exactly one newline boundary;
- verify exactly one `ZOSMA_CLI_VERSION=v0.0.0-dev` source assignment;
- preserve the final `main "$@"` contract;
- write a final newline and executable mode `0755`;
- support `--check` without modifying files; and
- never invoke a shell while assembling source.

No runtime dependency on `scripts/zosma-src` is allowed. A user downloading the raw artifact receives one executable.

### B. Staging is a real release, not a fake fixture

Add a manual `workflow_dispatch` path to `server-release.yml` with a generated prerelease version such as `v0.0.0-e2e.<run_id>`. It must:

- build from the selected branch commit;
- publish only to a uniquely named prerelease/tag and temporary GHCR tag;
- upload the same four archives, stamped CLI, `SHA256SUMS`, and `install-manifest.txt` consumed by the bootstrap;
- use a manifest URL supplied through `ZOSMA_TEST_MANIFEST_URL` when running the branch bootstrap;
- run the real raw branch `install.sh`, not a copied local fixture;
- run local and Docker smoke/lifecycle checks against those exact uploaded bytes;
- never update `releases/stable`, `latest`, production DNS, or production release assets; and
- clean up temporary prerelease/tag/container references only after logs and test results are retained.

The production tag path and staging path share packaging and verification steps. Only publication/promotion behavior branches by event type.

### C. Least-privilege release jobs

Keep permissions at job scope:

- build/package jobs: `contents: read`;
- GHCR job: `contents: read`, `packages: write`;
- attestation job: only the required artifact, `id-token`, and attestation permissions;
- release upload/promotion job: narrowly scoped `contents: write`; and
- stable-channel hosting job: only the credential required by the selected static host.

Every third-party action remains pinned to a full commit SHA. The workflow must fail closed if a required digest, asset, checksum, attestation, or release is missing.

## File plan

### New files

- `scripts/zosma-src/*.sh` — ordered maintainable CLI source fragments.
- `scripts/build-zosma.mjs` — deterministic standalone-artifact assembler.
- `scripts/build-zosma.test.mjs` — generator and artifact contract tests.
- `scripts/release-manifest.mjs` — pure manifest/checksum generation and validation helpers, if the existing packaging module cannot own them without coupling.
- `scripts/release-manifest.test.mjs` — malformed, duplicate, digest, basename, and cross-target coverage.
- `scripts/installer/staging-e2e.mjs` — exact prerelease bootstrap/lifecycle harness, with bounded child cleanup and no secret logging.
- `scripts/installer/staging-e2e.test.mjs` — command construction, URL pinning, cleanup, and failure-preservation tests.

### Modified files

- `scripts/zosma` — generated output only; no hand edits after extraction.
- `scripts/package-server-release.mjs` — expose reusable archive/stamp/checksum operations only where required.
- `scripts/package-server-release.test.mjs` — exact release asset and manifest coverage.
- `scripts/docker/server-release-workflow.test.mjs` — staging path, production path, permissions, action pins, attestations, and stable-promotion contracts.
- `.github/workflows/server-release.yml` — complete production and manual staging pipelines.
- `package.json` — `installer:build`, `installer:check`, and staging helper commands.
- `.github/workflows/ci.yml` — run generator check and the non-publishing contract suite; do not publish from ordinary PR CI.
- `README.md`, `docs/DISTRIBUTION.md`, `docs/installer.md`, and website installation content — update only after staging succeeds.
- Remove or label obsolete development-only server/sandbox paths only after the replacement path is demonstrated by staging.

## Merge and post-merge gates

The PR may merge only when:

- generated `scripts/zosma` is reproducible and all installer tests pass;
- the staging workflow has completed from the PR head;
- the real raw branch bootstrap consumed the temporary prerelease manifest;
- exact local and Docker artifacts passed verification and lifecycle smoke;
- failed-release tests prove stable-state preservation;
- CI, security, and review checks are green; and
- the PR body records that production stable promotion and DNS were intentionally not performed in PR staging.

After merge, production rollout is a separate controlled action:

1. Create a real semver tag after desktop release readiness is confirmed.
2. Let the production server workflow wait for the matching desktop release.
3. Verify uploaded artifacts, attestations, image digest, and smoke results.
4. Promote the stable manifest last.
5. Configure/verify `install.zosma.ai` and run the first beta release.
6. Repeat the rollout for a second consecutive release before calling the channel stable.

## Explicit non-goals

- Do not split the shipped CLI into runtime-loaded files.
- Do not add a second implementation of lifecycle behavior in JavaScript or Rust.
- Do not bypass checksum, manifest, digest, or attestation verification for staging.
- Do not publish `latest` or mutate `install.zosma.ai` from a PR workflow.
- Do not merge Phase 4 merely because unit tests pass while the exact artifact path is untested.
